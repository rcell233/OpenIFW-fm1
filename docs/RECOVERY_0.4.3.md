# 0.4.3：USB RESCUE 恢复候选（已被 0.4.4 替代）

> 后续仍反馈 USB RESCUE，实际安装版本未确认。软件已复现 0.4.2 / 0.4.3 在持续超时时占满 CPU、主循环无法喂看门狗的缺陷；请使用 [0.4.4 恢复说明](RECOVERY_0.4.4.md) 与当前安装入口。下文保留该版发布时的记录。

用户安装 0.4.2 后，网页报告最终固件身份不匹配，设备显示 OPENIFW FM1 USB RESCUE / CONNECT USB。**0.4.2 已撤出默认安装。** 0.4.3 恢复原平台的 XIP 链接布局，撤回新增 RAM DSP 搬运，保留音频 DMA 和等价性能修复。当前环境未连接设备，不能把软件通过当作实体恢复已确认。

## 从当前救援画面恢复

1. 保持设备在当前 USB RESCUE 画面并连接 USB；松开全部按键，尤其 OCT−。
2. 在 Chrome / Edge 打开 [修复版安装页](https://rcell233.github.io/OpenIFW-fm1/install/?v=0.4.3)，确认按钮为 **Install 0.4.3** 后安装。浏览器仍使用原 USB-MIDI 升级流程。
3. 安装和重启时不要按住 OCT−；它会主动触发救援模式。正常启动应回到原合成器界面。
4. 如果仍进入救援，可用 [回退到 0.4.1](https://rcell233.github.io/OpenIFW-fm1/install/?recovery=0.4.1&v=0.4.3) 恢复此前能启动的原包。回退包 SHA 与原发布版完全相同；它仍有此前的声音问题。

## 确认了什么

原平台的 `OTA_IDENTITY` 在救援分支报告 **FM-1_000**，正常程序报告 **FM-1_982**。安装器的最终确认因此拒绝成功是正确的，不应放宽身份检查。新页面会明确说明设备返回了救援模式，并提供恢复入口；普通安装和升级中断恢复两条路径均拒绝把救援当作成功。

救援可由 OCT− 开机或连续启动未成功的 bootguard 触发。仅凭当前画面无法区分，也没有设备上的异常 PC 或复位原因。**RAM DSP 是本轮撤回的首要新增启动风险，尚未证明它是唯一根因。** 指令模型先前能运行 0.4.2，未重现该实机问题。

## 构建变化

- 使用与 0.4.1 相同的原始平台链接脚本、crt0 和 RAM Flash driver；所有 DSP 回到 XIP。Flash driver 的 RAM 代码仍是 **2,848 B**，RAM DSP 为 **0 B**。
- 构建前重新创建暂存源码，防止复用旧变体的链接覆盖；构建前后校验原脚本哈希，检查核心 DSP 地址和 RAM 复制镜像，并保存实际链接脚本快照。
- 预设、矩阵、包络、单音 / Legato 及 DSP 数学源码与 0.4.2 相同。保留 DMA 入口确认、独立完成缓冲及约 5.805 ms 固定输出延迟，也保留 16 行显示调度。
- Pages 默认安装 0.4.3，单独提供经 SHA / CRC 校验的原始 0.4.1 回退包。安装页脚本使用版本地址，避免旧页面缓存混入恢复流程。

链接脚本 SHA-256：`6a9f41205e482fbdf2d24dc418416e45a3a8e1781d3e594279d751335af8942a`。发布包 SHA-256：`91c1bdb590b8d5b03a63d41703d8262f58d32b4249e20e2d0391516bfdd12d46`。

## 验证范围

`make test`、`make sanitize` 通过；166 场景的 332 份 PCM / 状态文件，以及 12 组旧 WASM 演奏 / 切页音频的 1,228,800 个立体声帧保持原值。UI 1,170 项、原生 C / WASM 逐字节对照、ASan / UBSan 均通过。

安装器 **83 项**检查包括从真实救援身份 FM-1_000 开始的完整镜像传输、原 0.4.1 包的完整回退传输，以及普通升级和中断恢复后返回救援身份的失败分支。它们是协议模拟，没有刷写实体设备。

目标 pi32v2 指令模型验证正常启动进入 app、OCT− 启动进入独立救援分支，以及 196,608 帧 / 24 个 IRQ 黄金校验值。六个工厂程序的完整 IRQ 峰值为 **3.994–4.811 ms**，模型内 XRUN / DMA 为 0。模型采用 240 MHz、除法 48 周期敏感性输入和 SPI 线速，不精确模拟 cache / Flash / 总线或 USB 主机；恢复 XIP 后的实际开销仍需在设备测量，也没有证明所有自定义组合都能实时运行。
