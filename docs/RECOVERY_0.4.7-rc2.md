# 0.4.7-rc2：启动恢复候选与救援诊断

用户实机安装 0.4.7-rc1 后，设备报告 FM-1_000 并显示 USB RESCUE。正常固件没有通过启动验收。**rc1 已撤出默认安装；默认入口恢复提供原始 0.4.6-rc2 包。0.4.7-rc2 通过独立候选入口选择；最新实机反馈已确认可以运行，JUDD 正常无爆音，Daisy / Tresure 仍有爆音，尚未完成声音验收。** 逐模块调查见 [音色负载分析](PRESET_COST_0.4.7-rc2.md)。

- [恢复原始 0.4.6-rc2](https://rcell233.github.io/OpenIFW-fm1/install/?recovery=0.4.6-rc2)：此前有 UI 流畅的实机反馈，声音问题仍在。
- [选择 0.4.7-rc2 恢复候选](https://rcell233.github.io/OpenIFW-fm1/install/?candidate=0.4.7-rc2&v=0.4.7-rc2)：恢复旧启动布局和分段合成，保留新界面，增加救援启动报告。
- [读取设备诊断](https://rcell233.github.io/OpenIFW-fm1/diagnostics/)：新候选在正常与 USB RESCUE 模式都支持“读取启动信息”。原始 0.4.6-rc2 不支持该协议。

## 调查结论与未确定项

rc1 将整块 256 帧合成放进 ALNK 中断，并把 TIMER5 和两个中断入口迁到 RAM。原来的两秒指令测试通过了装载、输入和正常启动，却没有覆盖真实 Flash/总线等待、USB 主机，也没有模拟看门狗复位。它不能证明实机长期运行，更不能否定本次硬件失败。

代码和此前压力模型已呈现一个明确风险：当中断内 DSP 连续超过 5.805 ms，ALNK 可以持续待决，主循环无法运行，影响看门狗喂养和 USB 控制。输入扫描搬入 RAM及强制内联也改变了执行位置和 GPIO 指令间隔；仅比较 C 语句相同不能证明外设时序正确。

**目前没有设备的重启来源与异常 PC，尚不能确认这两条路径中哪条触发了用户的救援状态。** 本版恢复已知可启动的关键路径，并提供下次故障所需的实际设备证据；不把推断称为已定位的实机根因。

## 恢复内容

1. 使用原始 vendor 的输入、时间和 ISR 汇编文件，恢复 0.4.6-rc2 的链接脚本。输入扫描与 ISR 包装在 Flash，DSP 与查表维持 rc2 的 RAM 布局。构建检查这三个中断符号的位置；vendor 文件不修改。
2. 恢复前台每次 32 帧的完整块生产队列，ALNK 中断只复制已完成的块及提供 USB Audio 数据。事件仍每 256 帧消费一次，所有合成采样按顺序推进。每个片段之间都会回到输入、USB、看门狗及显示调度。
3. 每个渲染片段通过 `in_audio` 延后完整 USB 轮询，ALNK 嵌套时保存并恢复原来的标志，避免中断返回后错误地解除渲染保护。中断没有被整个片段屏蔽。
4. 恢复有音频余量时绘图的策略；一块余量下仍给首页波形最高 10 Hz 的更新机会。保留纯色面板、清晰字体、原按钮和旋钮映射。REFRESH NORMAL / LOW 都继续显示波形。
5. 保存重启来源和软件启动阶段，保留原异常记录；在救援循环也服务只读诊断。看门狗、原启动保护和 FM-1_000 安装失败判定继续启用。

本版 DSP 源码与 rc1 相同，预设、矩阵、包络、采样率、单音与 Legato 行为不改。正在研究的“控制源 FM 项只计算一次”尚未放入这个恢复包。

## 启动信息

连接 MIDI 输入/输出，点击“读取启动信息”，即可下载 JSON。该操作不切换输出模式、不复位、不清除启动保护，也不写 Flash。

| 字段 | 含义 |
| --- | --- |
| `firmwareCode` | 40702 对应本恢复候选 |
| `entryReason` | 0 正常；1 连续启动失败后的自动救援；2 开机扫描检测到 OCT− |
| `p3Reset` / `resetSource` | 原 HAL 读取的复位源寄存器原值；P3 bit 2 是看门狗标志，需与其他字段一起判断 |
| `currentStage` | 当前启动进度；救援模式通常为 3，正常主循环为 11 |
| `previousStage` / `previousFirmwareCode` | RAM 中保留的上次进度与版本，只有运行过支持此功能的固件才有意义；断电或 loader 使用 RAM 可能使其丢失 |
| `crashValid` / `crashPc` 等 | 原 HAL 保留的异常记录；可能来自更早的运行，不能单凭一份记录断言属于本次固件 |

阶段：1 完成 RAM 初始化；2 启动保护与手动救援判定；3 进入救援；4 Flash/外设准备；5 音频外设准备；6 开启中断前；7 应用初始化；8 读取设置后；9 合成器初始化后；10 UI 初始化后；11 正常主循环。

正常模式的十秒性能采集继续可用。DSP 是各前台片段耗时之和；IRQ 是复制/USB 工作，两者和 rc1 的计时边界不同。XRUN 表示 DSP 块超预算，UND 表示播放时缺少完整块。协议中旧字段名 `missedCommits` 在本版对应 UND，不再代表 rc1 的提交守卫拒绝。

## 验证与限制

`make test`、原生 C/WASM、57 页交互、ASan/UBSan 与 115 项安装器模拟检查通过；包含从 FM-1_000 完整安装独立候选包以及默认仍选择旧恢复包。原有 166 场景、332 份 PCM/状态、12 组冻结演奏和实时编辑黄金值不变。目标 IRQ 流的 196,608 帧、24 个校验值与旧版一致。

原有音频和状态黄金值不更新。正常包、目标 IRQ 流变体和压力变体分别记录，发布的只包含正常包。测试及目标运行的具体结果见 [原始证据](evidence/recovery-0.4.7-rc2.json)。

生产调度功能测试在 5 倍预算的故意过载下，主循环最长间隔约 3.630 ms；输出缺块计数增加，未产生未完成的 DMA 数据。这验证前台可继续运行，不能证明声音实时达标。前台若有 40 ms 连续额外工作，仍会缺块，因此本版保留音频余量限制和分区绘制。

最终普通包在目标解释器运行 32 秒，主循环最长间隔 1 ms，30 秒后启动保护按原逻辑清除；物理 OCT− 救援、保留阶段和原 RAM 装载检查通过。10 秒目标压力变体仍有 174 次缺块、DSP 峰值约 6.474 ms，但主循环最长间隔 2 ms 并继续绘图，显示过载没有再把前台完全占住。模型仍不模拟真实看门狗复位、Flash/cache/bus 等待或 USB 主机。启动与声音最终都需实机确认。
