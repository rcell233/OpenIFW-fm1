# 0.4.4：修复持续音频超时导致主循环饥饿

设备仍反馈 USB RESCUE（FM-1_000），当前设备实际安装版本未确认。本版修复了软件已复现的中断饥饿缺陷，保留 0.4.3 恢复的原始 XIP 链接布局。开发环境没有连接设备，尚不能断言实机救援的全部原因已经解决。

## 安装与回退

1. 保持当前 USB 连接，松开全部按键，尤其 OCT−。
2. 打开 [0.4.4 安装页](https://rcell233.github.io/OpenIFW-fm1/install/?v=0.4.4)，确认按钮显示 **Install 0.4.4** 后安装。安装与重启时都不要按住 OCT−。
3. 如果仍停在救援画面，使用 [回退到 0.4.1](https://rcell233.github.io/OpenIFW-fm1/install/?recovery=0.4.1&v=0.4.4) 恢复此前可启动的原始包；该版本仍有原来的音频问题。

正常身份仍为 FM-1_982；FM-1_000 表示救援。安装器继续拒绝把救援当作成功，不修改设备身份、看门狗或启动保护。

## 已复现的问题

0.4.2 / 0.4.3 为避免清掉新的 DMA 边界，改为在音频中断入口确认 HALF。若每次合成持续超过 5.805 ms，下一个 HALF 在返回前已到达，中断就会连续执行，主循环没有机会处理输入、USB 和喂看门狗。原平台看门狗时限为 8 秒；连续启动失败又可能触发 bootguard 救援。这是已复现的故障机制，尚未证明它就是本次设备进入救援的唯一原因。

运行真实 C ISR 的采样时钟测试持续 10 秒：旧版在仅 1% 超时时，主循环仍只能运行一次，最长间隔超过 10 秒；新版在 1%、25%、80% 超时下注入让出机会，主循环最长间隔为 52.7、63.9、89.4 ms。全部 DMA 数据仍是完成的 Q24 格式。渲染耗时是测试输入，不是芯片测量值。

实际编译的 pi32v2 固件又做了独立过载对照：人为将模型设为 160 MHz，除法假设 48 周期、开启 SPI 线速等待，运行 10 秒。旧版主循环执行 **0 次**，末次服务距当前 **10,000 ms**；0.4.4 执行 **291 次**，最长服务间隔 **638 ms**，末次距当前 **12 ms**，保护让出 **165 次**。这说明保护能在该负载模型下恢复主循环，不代表实体 CPU 是 160 MHz，也不代表模型验证了真实看门狗复位。

## 修复行为与边界

连续 8 次迟到后，下一次中断只发布上一块已经完成的音频，不再立刻计算一块 DSP，留出主循环的运行窗口；下一个真实 DMA 边界恢复渲染。预设、矩阵、包络、单音 / Legato 和 DSP 数学源码不变，正常按时完成时保护不会触发。

**持续过载时仍可能重复旧音频块，声音和节奏不能保证正常。** 本次保护解决 CPU 一直被音频占住的问题，不把超预算配置伪装成性能达标，也不通过减少振荡器、效果器或调制链路降低音色复杂度。

## 测试与发布包

`make test`、`make sanitize` 通过。166 场景的 332 份冻结 PCM / 状态、12 组冻结 WASM 演奏共 1,228,800 个立体声帧保持原值；原生 C / WASM 逐字节一致。UI 1,170 项、安装器 83 项（含救援完整安装、原包回退、拒绝重启后救援身份）通过。旧版饥饿与新版有界服务测试已加入持续集成。

目标指令模型的正常启动、OCT− 救援启动，以及 196,608 帧 / 24 个 IRQ 黄金校验值通过。240 MHz 模型内六个工厂程序在 1 秒后的完整 IRQ 峰值为 **3.994–4.811 ms**，全过程 XRUN、DMA、保护让出均为 0。模型不精确模拟 cache、Flash、总线或连接的 USB 主机，不能替代实机测试。

发布包 **610,110 B**，应用 **224,872 B**，data+bss **31,344 B**，效果器池 **294,216 B**；DSP 在 XIP，RAM 代码仍只有原 Flash driver 的 **2,848 B**。原始链接脚本 SHA-256 为 `6a9f41205e482fbdf2d24dc418416e45a3a8e1781d3e594279d751335af8942a`。

发布包 SHA-256：`39fb0338e9c12394897edd62b19902af1f82b324c03628ee102c7d8c9ec1af8e`。重新构建得到相同字节。0.4.1 回退包保留原 SHA：`cf7ab1e35378ae7797ab817c7e32aaa8ce0b49d3bbbe55185aa18ded7ae2a9b8`。

正常界面恢复后，按 [上板测试](HARDWARE_TEST.md) 查看 PERFORMANCE 的 MAX / XRUN / DMA，并比较 SINE 与 SYNTH。完整机器可读结果见 [验证证据](evidence/recovery-0.4.4.json)。
